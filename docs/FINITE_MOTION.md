# 有限运动控制：从代码到现场准备

本页用于理解实现。公开仓库不提供针对读者设备的已批准动作计划；先完成[离线快速开始](QUICKSTART.md)和[只读查询](HARDWARE_AND_ROS2.md)，再核对自己的设备、供电、装配、场地与实际状态。

## 一次单轴动作经过哪些步骤

ROS 入口位于 `ros2_ws/src/jixiebi_driver/jixiebi_driver/single_sweep.py`，计划解析在 `src/arm_project/ros_sweep.py`，连续动作和精确帧门禁在 `src/arm_project/joint_sweep.py`：

1. 本地计划明确舵机编号、协议位置 P 的起点与观察区间、目标、毫秒时长和唯一审阅标识，还要包含六轴起始范围。P 不是角度或毫米。
2. 节点独占串口并读取各轴当前状态；依次读取并非同时采样。检查运动轴型号、模式和起点，记录一次性预算，才可能发送一条目标。
3. 运动中查询目标轴反馈并记录，检查方向、范围和超时。当前实现不会持续监控其余轴；不得据此认为全臂无碰撞。
4. 返回区分有向响应、严格到位、无需运动、取消和失败。异常不会自动重试；发送停止帧或收到软件取消结果不证明设备已物理停止。

ROS 节点的 `/jixiebi/sweep/execute` 和 `/jixiebi/sweep/cancel` 是 `std_srvs/srv/Trigger` 服务，接收的是触发请求，具体动作取自启动时加载的本地计划，不在网络消息里接收任意帧。**服务没有内建身份认证**，应限制网络访问；不要把动作服务暴露给不可信网络。

本项目的 Windows/Linux 示例、旧实验坐标和舵机 P 值不能直接当成你的设备可执行范围。布置场地、单串口所有者、路径审核、紧急处置、限位、真实坐标和动作预算均需按实际硬件单独确认，不能用厂家标称模型代替实测。40–50P 是项目初期的软件探测窗口，不是厂家机械极限。

## 理解底层协议

`src/arm_project/servo_protocol.py` 负责组装和解析帧，`arm_link.py` 管理串行事务。如下只是格式示例，**不应直接粘贴到串口执行**：

```text
#004PRAD!         查询 004 号舵机位置
#004P1540T1500!   请求目标 1540P，声明时间 1500 毫秒
```

帧写入成功只说明主机提交了数据，不能证明舵机已达到目标；回包也不包含设备采样时间戳或请求序号。真实夹持、空间精度和物理停止各需单独证据。
